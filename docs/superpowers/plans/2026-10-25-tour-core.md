# Tour Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tours with ordered stops + full manifest, fastest-time auto-order, tap+GPS PoD, skip-with-reason, per-leg dispatch_route chain.

**Architecture:** `tour` row owns ordered `tour_stop` rows. Dispatch validates leg 1
(origin→stop1) into a `dispatch_route` with `tour_id` set; each PoD/skip validates the
next leg and assigns a new route. `TourOptimizerService` orders stops via Google
`computeRouteMatrix` (TRAFFIC_AWARE) when keyed, haversine fallback otherwise; NN + 2-opt
in both paths. Tour row is pessimistically locked during advance.

**Tech Stack:** Java 21, Spring Boot 3.5, PostGIS/JTS, Flyway, JUnit 5 + Mockito (+ Testcontainers for repo test).

**Spec:** `docs/superpowers/specs/2026-10-25-tour-engine-design.md`

## Global Constraints

- Java 21, Spring Boot 3.5, PostGIS, Flyway append-only (this slice: V34).
- Google Routes `computeRouteMatrix` only when `google.routes.api-key` set; else haversine fallback, never fail.
- v1 cap: 12 stops per tour.
- Only the assigned driver advances stops; only while tour ACTIVE.
- A failed stop never freezes a tour; skip keeps original order (no mid-tour re-optimization).
- Signed commits (`git commit -s`).

## Review Focus

- 13th stop rejected with 400, not a silent truncate — needs a test in Task 1.
- Advance by a different driver is 403 — test in Task 3.
- PoD twice on the same stop is idempotent-ish (second returns current state, no duplicate leg) — test in Task 3.
- Google key absent: dispatch still succeeds via haversine order — test in Task 2/3.
- Skip of the last stop completes the tour, not strands it — test in Task 3.
